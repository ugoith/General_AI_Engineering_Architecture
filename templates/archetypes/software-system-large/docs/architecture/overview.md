## 2. 子系统划分

模块数量在 15–60 之间，必须分组为**子系统**，否则没人能记住边界。每个子系统有 owner，内部模块可自由重构，跨子系统只能走公开契约。

```text
[接入子系统: api / cli / ui]
          |
          v
[业务子系统 A: <module-a>, <module-b>]  --事件-->  [业务子系统 B: <module-c>]
          |                                              |
          v                                              v
[平台子系统: db / queue / 观测 / 配置]  （不反向依赖业务）
```

## 3. 模块表

| <子系统 A> | `<module-a>` | (示例) 订单生命周期 | (示例) 不负责计价 | `{{srcDir}}/modules/<module-a>/public` | pricing, db | <@team> |

权威的机器可读登记在 `{{aiDir}}/registry.json`（`kind: module`）；两处的 `owner` 必须一致。

## 4. 依赖方向与规则

- 允许方向：入口 → 业务 → 平台；同层依赖必须显式声明，禁止反向与跨层直连。
- 规则编号、检查方式与例外表：`{{docsDir}}/architecture/dependency-rules.md`（CI 强制）。
- 违反边界时的三条出路（下沉共同依赖 / 改事件或上层编排 / 合并模块）：见 `{{srcDir}}/modules/README.md`。

## 6. 跨模块协作约定

| 项 | 约定 |
|---|---|
| 同步调用 | 必须约定超时与错误码；禁止跨模块层层重试 |
| 事件 | 至少投递一次 + 消费方幂等；载荷字段只增不删 |
| 一致性 | 明确哪里是最终一致；不一致时用户看到什么，写清楚 |
| 失败 | 部分失败必须可观测（日志/指标），不允许静默吞掉 |

## 7. 关键约束

- 契约与版本策略：`{{docsDir}}/architecture/contracts/README.md`
- 数据所有权与不变量：`{{docsDir}}/architecture/data-model.md`
- 接口契约与兼容矩阵：`{{docsDir}}/architecture/interfaces.md`
- 性能预算：`{{docsDir}}/architecture/performance-budget.md`
- 本规模禁止项（无 ADR 的跨模块重构、隐式全局状态、绕过契约层的跨模块直连）：见 `{{aiDir}}/constitution.md`

## 8. 维护与评审

- 改边界或主数据流：先写 ADR → 改本文件 → 按 `{{aiDir}}/index/impact-map.json` 同步 registry、依赖规则与索引。
- 固定节奏评审时核对：模块表与 `{{srcDir}}/modules/` 目录是否一致；依赖规则例外表是否全部到期处理；预算是否仍在有效期内。
