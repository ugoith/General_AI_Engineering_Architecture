# 性能预算（L 级）

> 目的：把"感觉有点慢"变成**可判定、可追责的数字**。没有预算的性能优化必然是随机的：有人凭直觉优化，有人凭直觉引入回归。
> 规则：表里每个指标都必须有**测量方式**与 **owner**；写不出测量方式的指标不要放进这张表。

## 1. 预算表

数值为示例格式，替换成真实数字；"当前"列每次基准测试后更新，并保留测量日期。

| 指标 | 预算 | 当前 | 测量方式 | 测量环境 | owner |
|---|---|---|---|---|---|
| 冷启动时间 | ≤ 800 ms | <值> (<日期>) | `bench startup --runs 20` 取中位数 | 本地容器，2 vCPU / 4G | <@team> |
| 关键接口 P95 延迟 | ≤ 300 ms | <值> (<日期>) | `bench api --path <关键路径> --p95` | 预发环境，单实例 | <@team> |
| 单请求数据库查询数 | ≤ 3 | <值> (<日期>) | 查询计数器断言（契约测试内） | 本地 | <@team> |
| 常驻内存峰值 | ≤ 512 MB | <值> (<日期>) | `bench memory --duration 60s` | 本地容器 | <@team> |
| 全量构建时长 | ≤ 120 s | <值> (<日期>) | CI 构建步骤耗时 | CI runner | <@team> |
| 发布产物体积 | ≤ 50 MB | <值> (<日期>) | 构建产物打包后统计 | CI | <@team> |

选取原则：每个指标对应一个**用户能感知或成本会失控**的量；不要为无法影响决策的数字建预算。

## 2. 测量方式怎么写

一条合格的测量方式包含四件事：**命令**、**环境**、**样本量或统计口径**（中位数 / P95）、**可复现的前提**。

- 反例：`"本地跑一下挺快的"`、`"感觉不到卡"`、`"测了 1 次"`。
- 正例：`bench startup --runs 20 --warmup 3`，取中位数，本地容器 2 vCPU。
- 基准脚本随代码入库（放在 `{{testsDir}}/bench/` 或等价目录），并在 `{{aiDir}}/constitution.md` 的验证命令里登记。

## 3. 超标怎么办

1. **复测**：换一次环境和样本量复测，排除噪音；把两次结果都记进任务包"证据"。
2. **定位**：把超标归因到模块或提交（用 `review --impact <改动文件>` 缩小范围），不要停在"系统变慢了"。
3. **二选一**：
   - 修复：回到预算内，并补一条能防回归的检查；
   - 调整预算：写 ADR，说明为什么这个数字不该继续约束（含业务理由与替代控制手段），并更新本表。
4. **记录**：无论哪种，都要更新"当前"列与日期；静默超标是最坏的结果。

## 4. 何时更新

| 对象 | 时机 | 谁 |
|---|---|---|
| 预算值 | 架构变化、业务目标变化、或连续两个周期超标 | 模块 owner 提议 + ADR |
| 当前值 | 每次基准测试 / 每次 CI 跑基准后 | 提交者 |
| 测量方式 | 环境或工具链变化时（改完要重新建立基线） | 基础设施 owner |
| 指标集合 | 每次架构评审（删掉没人看、无法影响决策的指标） | 评审 |

## 5. 与 CI 的关系

- 至少把"构建时长"和一项运行期指标接进 CI：超标即失败（硬指标）或告警 + 趋势记录（噪音大的指标）。
- 噪音大的指标先只做趋势记录，稳定后再升级为失败条件；否则会因为抖动被整体关闭。
- 基线数字必须与代码一起演进：改了测量方式就要重建基线，否则比较没有意义。

## 6. 反例

| 反例 | 为什么坏 |
|---|---|
| 预算写成"尽量快" | 无法判定，也无法追责 |
| 只测一次就宣布达标 | 单次测量没有统计意义 |
| 超标后直接改预算数字 | 预算变成装饰；改预算必须写 ADR 并说明替代控制 |
| 指标归到"整个系统" | 无法定位到模块，也就没人负责 |
