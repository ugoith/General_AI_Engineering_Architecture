# 依赖规则与自动化检查（L 级）

> 目的：把"模块之间允许怎么依赖"从口头约定变成**能失败的检查**。
> 判断标准很简单：如果一条规则不能在 CI 里失败，它就只是建议；L 级不接受只存在于文档里的边界。

## 1. 规则表

规则编号与 `{{srcDir}}/modules/README.md` 保持一致；新增规则必须同时改两处。

| 编号 | 规则 | 级别 | 检查方式 | 违反处理 |
|---|---|---|---|---|
| R1 | 跨模块只引用对方的 public 出口 | error | 导入图分析脚本 | 阻断合并 |
| R2 | 依赖方向单向：入口 → 应用 → 领域；基础设施不反向依赖业务 | error | 分层白名单检查 | 阻断合并 |
| R3 | 禁止循环依赖 | error | 导入图找环 | 阻断合并 |
| R4 | 领域层不依赖框架、IO、网络 | error | 导入白名单 | 阻断合并 |
| R5 | 只有 owner 能写自己的数据；跨模块写必须经公开接口 | error | 存储访问点检查 + 评审 | 阻断合并 |
| R6 | 共享模块不得反向依赖任何业务模块 | error | 导入图分析 | 阻断合并 |
| R7 | 未登记的新模块不允许被引用 | warn | 目录与 registry 比对 | 评审时补登记或删除 |

级别说明：`error` 会让 CI 失败；`warn` 只记录，但连续两个评审周期未处理就升级为 error。

## 2. 检查怎么接进 CI

按成本从低到高，先做能跑起来的那一条：

1. **导入图脚本**：遍历源码提取导入关系（可参考 `.ai/index/files.json` 里的 `imports` / `importedBy`），与规则表比对，违反则退出码非 0。零依赖，最容易落地。
2. **linter 规则**：把禁止的导入路径写成 lint 规则（各语言生态都有现成机制）。
3. **构建系统边界**：用多模块构建（每个模块独立声明可见依赖）让违规在编译期失败，最强也最贵。

接入要求：

- 检查命令必须写进 `{{aiDir}}/constitution.md` 的"验证命令"表，和测试一样每次提交都跑。
- 输出要能定位到文件与行号，禁止只输出"发现 N 处违规"。
- 规则配置随代码入库、可评审；不要放在某个人的本机配置里。

## 3. 例外表（唯一合法的绕过方式）

| 编号 | 规则 | 位置 | 理由 | ADR | 到期复审 | owner |
|---|---|---|---|---|---|---|
| (示例) EX-1 | R4 | <某适配器文件> | 该文件就是防腐层，必须接触外部 SDK | ADR-0007 | 2025-06-30 或下次重构 | <@team> |

例外必须：有 ADR、有到期时间或明确的复审触发条件、有 owner。到期的例外自动失效——要么修好，要么重新申请。

## 4. 违规处理流程

1. **确认**：本地跑一次规则检查命令，拿到文件与行号，不要凭印象争论。
2. **判断**：这是实现问题还是规则问题？实现问题就改实现；规则过严就按第 5 节改规则并写 ADR。
3. **记录**：确实无法立刻修的，进第 3 节例外表，写清到期条件。
4. **回归**：补一条能覆盖该场景的测试或检查，防止再次出现。

## 5. 新增规则怎么加

- 从**真实发生过的违规**倒推规则，不要预防性制造规则（会得到一堆没人遵守的禁令）。
- 新规则先进 `warn`，观察一个周期后再升 `error`。
- 改规则 = 改架构约束：必须写 ADR，并更新 `{{docsDir}}/architecture/overview.md`。
- 相关触发条件见 `{{aiDir}}/index/impact-map.json` 的 `dependency-rule-change`。

## 6. 反例

| 反例 | 为什么坏 |
|---|---|
| 规则只写在文档里，CI 不检查 | 第一个赶工期的人就会破例，之后成为惯例 |
| 例外不留到期时间 | 例外变成永久豁免，规则名存实亡 |
| 检查输出只报总数 | 无法定位，等于没有可操作性 |
| 一次性加十几条规则 | 规则太多会被整体忽略；先加最痛的一条 |
