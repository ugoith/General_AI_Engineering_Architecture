# 模块边界规则

> 模块 = **可以独立修改、独立测试、有明确所有者的单元**。这些规则的目的：让 AI 和新人不必读完整个仓库，就知道"能碰什么、不能碰什么"。
> 违反边界不是风格问题，是缺陷来源：它会制造隐式耦合，让改一处坏三处。

## 1. 目录约定

```text
{{srcDir}}/modules/<module>/
  public.<ext>        # 唯一出口：其它模块只能引用这里导出的符号
  ...                 # 其余文件都是内部实现，外部不得引用
{{testsDir}}/modules/<module>/    # 该模块自己的测试
```

- 每个模块必须有且只有一个公开出口（名字按语言惯例：public.ts / __init__.py / Module.cs …）。
- 内部文件可以自由重构；只要 `public` 签名不变，就不算破坏性变更。
- 模块的职责写在 `{{docsDir}}/architecture/overview.md` 的模块表里，缺一行就等于没有边界。

## 2. 三条硬规则

| 编号 | 规则 | 违反示例 |
|---|---|---|
| R1 | 跨模块只能引用对方的公开出口 | 从 a 模块直接 import b 模块的内部文件 |
| R2 | 依赖方向必须单向：上层依赖下层，禁止反向；同层依赖要显式声明 | 领域层 import 了 HTTP 处理层 |
| R3 | 禁止循环依赖（a→b→a） | a 调 b 的工具函数，b 又调 a 的校验函数 |

## 3. 依赖方向

分层名与允许方向按项目实际情况填下表（改这张表 = 改模块边界，需要 ADR）：

| 层 | 模块（示例） | 允许依赖 | 明确禁止 |
|---|---|---|---|
| 入口/接口层 | api, cli, ui | 应用层 | 基础设施细节（SQL、SDK 客户端） |
| 应用层 | orders, billing | 领域层、下层模块的 public | 直接操作存储 |
| 领域层 | pricing, rules | 无（或仅标准库） | 框架、IO、网络、其它层 |
| 基础设施层 | db, http, queue | 无 | 反向依赖业务模块 |

同层之间允许的调用方向要写清楚（例如"orders 可调 pricing，反之不行"）；没有写清的调用，评审时按违规处理。

## 4. 循环依赖怎么处理

1. **先确认**：用导入图确认环的两端（`review --impact <文件>` 会列出 `importedBy`）。
2. **三选一，并写进 ADR**：
   - 提取共同依赖：把双方都要用的部分下沉到第三个模块；
   - 反向调用改事件/回调：由上层统一编排，双方不再互相调用；
   - 合并模块：如果两边总是一起改，它们本来就是一个模块。
3. **不要**用"延迟导入""全局单例""运行时反射"绕过环——那只是把循环藏起来。
4. 处理完更新 `{{docsDir}}/architecture/overview.md` 的模块表与依赖方向。

## 5. 新增模块清单

- [ ] 职责一句话可说清，且不与现有模块重叠；写入架构概览的模块表
- [ ] 建 `{{srcDir}}/modules/<module>/` 与 `public` 出口，明确 owner
- [ ] 依赖方向符合上表；不引入环
- [ ] 写 ADR（`{{aiDir}}/decisions/`），说明为什么现有模块放不下
- [ ] 补最小测试；在 `{{aiDir}}/registry.json` 登记该模块实体
- [ ] 更新索引：`node {{aiDir}}/bin/ai-arch.mjs index`

## 6. 反例

| 反例 | 为什么坏 |
|---|---|
| 建一个 `utils` / `common` / `shared` 模块放"暂时不知道放哪"的代码 | 它会变成所有模块的隐式依赖，改一行波及全仓库 |
| 用"只有这次特殊"作为跨模块深引用的理由 | 一次深引用会变成下一次的默认做法 |
| 把两个模块互相需要的数据塞进全局状态 | 依赖关系从代码里消失，评审与测试都看不见 |

## 7. 自动化检查

- 静态检查：用语言的导入分析能力（或 ESLint/ArchUnit/import-linter 等工具）把 R1–R3 变成 CI 里的失败项；规则配置与豁免清单放在仓库内、可评审。
- 人工兜底：CI 未覆盖语言时，在评审清单里加一条"跨模块引用是否只走 public"。
- 影响面：改模块边界前后跑 `node {{aiDir}}/bin/ai-arch.mjs review --impact {{srcDir}}/modules/<module>`，核对受影响的文件与测试。
- 相关规则：`.ai/index/impact-map.json` 的 `module-boundary-change`。
