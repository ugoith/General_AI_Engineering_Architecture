# 蓝图 vs C++：职责边界判定

> 争议点永远在这句上：*"这段逻辑该写 C++ 还是蓝图？"*
> 本文给可执行的判定顺序与清单，避免"两处真相"和"规则藏在资产里"。
> 前提：本项目当前形态为 {{#IF usesBlueprint}}**C++ + Blueprint 混合**{{/IF}}{{#UNLESS usesBlueprint}}**纯 C++**（引入蓝图资产需先写 ADR）{{/UNLESS}}。

## 1. 一句话原则

**C++ 定义"是什么与怎么算"，蓝图定义"用哪些、摆在哪、看起来怎样"。**
凡是"能被自动化测试断言的规则"都属 C++；凡是"美术/策划在编辑器里迭代的表现"都属蓝图。

## 2. 判定顺序（从上到下，命中即停）

1. **它是规则还是表现？** 规则（伤害公式、冷却、状态机、掉落逻辑）→ C++。
   表现（特效触发时机、材质参数、动画蒙太奇选择）→ 蓝图。
2. **它会参与存档 / 网络复制 / 自动化测试吗？** 任一为"是" → C++。
3. **策划需要频繁调数值吗？** 需要 → C++ 读 DataAsset（数值在资产里，逻辑在 C++），**不是把逻辑搬进蓝图**。
4. **它需要 Tick 且对性能敏感吗？** 是 → C++（蓝图 Tick 成本高且难 profile）。
5. **它只在编辑器里跑吗？** 是 → 编辑器工具（C++ 或 Editor Utility），不要混进运行时蓝图。
6. **它是纯装配（把组件、资产、事件连起来）吗？** 是 → 蓝图。
7. **它是美术/策划的日常迭代对象吗？** 是 → 蓝图（放在明确的"表现层"目录）。
8. 以上都不命中 → **默认 C++**（因为可测试、可 review、可 diff）。

## 3. 职责分配表

| 内容 | 归属 | 理由 |
|---|---|---|
| 伤害/命中/暴击计算 | C++ | 规则，必须可测试 |
| 状态机（移动、战斗状态） | C++（数据驱动） | 规则；状态数据放 DataAsset |
| 数值配置（血量、攻击力、曲线） | DataAsset / DataTable | 策划可调，无需重编译 |
| 输入映射资产（`IMC_`/`IA_`） | 资产（`Core/`） | 输入配置本身是数据 |
| 角色 Actor 装配（挂哪些组件） | 蓝图（子类） | 典型装配工作 |
| 特效/音效触发时机 | 蓝图（接收 C++ 事件后播放） | 表现，需要美术迭代 |
| 动画蓝图与混合空间 | 蓝图 | 表现 |
| UI 布局与动画 | UMG 蓝图 | 表现 |
| UI 与游戏的绑定逻辑 | C++ 暴露接口 + 蓝图绑定 | 绑定是可变的，接口必须稳定 |
| 关卡摆放、光照、触发器 | 关卡（Map） | 关卡设计 |
| 存档序列化格式 | C++ | 契约，必须可测试、可迁移 |
| 网络复制属性与 RPC | C++ | 契约与安全 |
| 编辑器批量工具 | C++ 编辑器模块或 Editor Utility | 可脚本化、幂等 |

## 4. 与用户对齐：什么时候必须停下来问

判定顺序能处理**已有先例**的分配；但游戏项目的边界是**团队习惯 + 迭代方式**的产物，不是纯技术推导。
以下情况**必须先与用户对齐再动手**——因为选错的代价不是"重写一个函数"，而是"这套内容以后都难改"。

### 4.1 触发条件（命中任一即停下问，不要自行决定）

| 触发 | 为什么要问 |
|---|---|
| 要新增一类**跨系统**内容（技能体系、状态体系、AI 行为体系） | 它决定后续所有同类内容放哪；一旦铺开再迁移成本极高 |
| 要决定"某类内容**一律**用蓝图 / 一律用 C++" | 这是长期约束，属于架构决策，不是实现细节 |
| 现有代码里**同类逻辑有多套实现**（C++ 一份、蓝图一份） | 先问清哪份是权威、另一份是否要废弃，否则会继续长出第三份 |
| 该内容的**迭代者不是写代码的人**（策划/美术要天天改） | 迭代方式决定载体；用 C++ 会让他们无法改，用蓝图则可能不可测试 |
| 该内容**参与存档 / 网络复制 / 回滚** | 契约必须在可测试的一侧；但若团队已有既定做法，需沿用 |
| 需要为蓝图暴露**新接口**（`BlueprintCallable` / `BlueprintImplementableEvent`） | 暴露即契约，会影响所有蓝图调用方 |
| 团队里**已有既定规范**（例如"所有 UI 逻辑走蓝图"） | 与本文档冲突时以团队既有规范为准，并把差异记入 ADR |

### 4.2 对齐时该问什么（照这五问，不要泛泛地问"你想怎么写"）

1. **谁改它？** 你（程序员）/ 策划 / 美术 / 都要改 → 决定载体（能改的人必须改得动）。
2. **多久改一次？** 每天调 / 每月 / 一次成型 → 频繁调的内容不该需要重编译。
3. **错了会怎样？** 数值错了可接受 / 状态错了会出漏洞 / 存档错了会掉档 → 决定是否必须可测试。
4. **要不要能被自动化测试断言？** 要 → C++（蓝图难以进入自动化测试）。
5. **这份内容有没有已有的先例？** 有 → **沿用先例**（一致性优先于本次的最优解）；没有 → 按第 2 节判定顺序，并把结论写下来。

### 4.3 对齐结果记在哪（三处，缺一不可）

| 记在哪 | 记什么 |
|---|---|
| `.ai/rules.json`（`ai-arch rules add`） | 若结论是"某类内容一律用 X"→ 作为**项目规则**入库，这样每次任务包都会带上它 |
| `.ai/decisions/`（ADR） | 结论与**回退条件**（什么情况下应该推翻这个分配） |
| 本文档第 3 节职责分配表 | 具体条目的归属，作为后续同类内容的先例 |

**只口头对齐 = 没对齐**：下一次任务（可能是另一个 agent、可能是三个月后）看不到那次对话。

### 4.4 对齐的记录模板（直接复制到 ADR）

```markdown
## 背景
需要新增 <内容>，涉及 <系统A> 与 <系统B>，当前无先例。

## 五问结论
- 谁改它：<策划每天调数值 / 只有程序改>
- 多久改一次：<每月 / 每次版本>
- 错了会怎样：<数值偏差可接受 / 会导致存档损坏>
- 要不要自动化测试断言：<要 / 不要>
- 有无先例：<无 / 有：见 xxx>

## 决定
<逻辑在 C++ 的 XxxComponent；数值在 DA_Xxx；表现与装配在 BP_Xxx>

## 后果与回退条件
- 代价：<改规则需重编译；策划改数值不需重编译>
- 回退条件：<若策划需要改的是规则而非数值，则重新评估是否改为数据驱动解释器>
```

## 5. 反模式（评审直接退回）

| 反模式 | 危害 |
|---|---|
| 蓝图中实现一套伤害公式，C++ 里也有一套 | 两处真相，改一处必漏一处 |
| 蓝图 `EventGraph` 里堆业务规则，靠注释解释 | 不可 review、不可 diff、不可测试 |
| 蓝图 `Tick` 里做全场景遍历 | 性能黑洞，且难定位 |
| 用蓝图变量做跨系统状态（谁都能改） | 隐式全局状态，竞态与难复现 bug |
| 把"因为改 C++ 要重编译"当作写蓝图的理由 | 重编译成本 << 规则不可测试的长期成本 |
| 蓝图里硬编码资产路径（`LoadObject` 字符串） | 改名即静默失败；应走 `UPROPERTY(EditDefaultsOnly)` 引用 |
| 把 DataAsset 的子类逻辑写在蓝图里 | 数据与规则混一起，无法校验 |

## 6. 边界变更的处理

以下改动属于**边界变更**，必须先写 ADR（`{{aiDir}}/decisions/`）：

- 把一段规则从蓝图迁移到 C++（或反向）。
- 为蓝图新增 `BlueprintCallable`/`BlueprintImplementableEvent` 接口（= 对外契约）。
- 新增蓝图层（例如引入"数据驱动技能"体系）。
- 决定"某类内容一律用蓝图/一律用 C++"（这类决定会长期约束后续选择）。

迁移做法（蓝图 → C++）：
1. 用索引条目确认该蓝图的 `class` 与 `deps`；
2. 在 C++ 里实现等价规则 + 单元测试（自动化测试能断言）；
3. 蓝图改为调用 C++ 接口，删除重复逻辑；
4. 更新 asset-index 条目（`class`/`purpose`/`deps`）与 `files.json`；
5. 跑 L1 测试 + 手动过一次相关流程，把证据写进任务包。

## 7. 何时**应该**用蓝图（防止过度 C++ 化）

- 装配与连线：把 C++ 组件、DataAsset、输入动作连起来。
- 表现迭代：特效、音效、UI 动画、镜头抖动。
- 关卡内的临时脚本：原型验证用，验证完要么转正（迁移到 C++）要么删除，**不允许长期停留**。
- 策划可配的组合逻辑：用数据 + C++ 解释器，而不是在蓝图里连 40 个节点。
