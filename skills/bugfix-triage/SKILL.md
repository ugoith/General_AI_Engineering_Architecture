# 缺陷定位与修复

## 铁律：先复现，再修

没有稳定复现的修复等于赌博。三次"试着改改"比一次定位更贵，而且会污染代码。

## 流程（七步）

### 1. 记录现象（不解释）
写清楚：**输入 → 实际输出 → 期望输出 → 发生频率**。
不要在这一步写猜测原因（会把后续排查引向错误方向）。

### 2. 稳定复现
- 写一个失败的最小用例（脚本/测试/命令）。
- 若无法复现：记录环境差异（版本、配置、并发、数据），并把"无法复现"本身写进任务包 —— **不要**凭猜测改代码。

### 3. 缩小范围（二分）
- 代码二分：注释/短路一半逻辑，看是否还复现。
- 时间二分：`git bisect`（有测试可用时最有效）。
- 数据二分：用最小输入，逐步加回字段直到复现。

### 4. 形成假设（一次一个）
写下："我认为 X 导致了 Y，**因为 Z**"。一次只验证一个假设。

### 5. 验证假设
在假设成立的位置打断点/加日志/写断言。**要能观察到"假设不成立"的证据**，否则不是验证。

### 6. 修复并加回归测试
- 修**根因**，不是症状。判断方法：问"如果换个入口调用，这个问题还会出现吗？"
- 加一个能复现原问题的测试；变绿后故意改坏实现，确认测试会红。

### 7. 记录
任务包第 5/6/7 节：根因、证据、为什么这样修、同类问题是否还存在。
若根因是**结构性**的（依赖关系错误、缺少契约校验），写 ADR 或往影响矩阵加规则。

## 常见根因分类（先按类别排查更快）

| 类别 | 典型表现 | 排查手段 |
|---|---|---|
| 状态污染 | 单独跑通过、一起跑失败 | 检查全局/单例/静态缓存；测试间共享状态 |
| 时序/并发 | 偶发、与负载相关 | 加日志时间戳；检查共享可变状态与信号顺序 |
| 边界/空值 | 特定输入才失败 | 检查空、0、负数、超长、Unicode、时区 |
| 契约不一致 | 前后端/模块间字段对不上 | 对账 `.ai/registry.json` 与真实实现 |
| 环境差异 | 本机通过、CI 失败 | 对比版本、路径大小写、换行符、时区、locale |
| 资源泄漏 | 运行一段时间后变慢/崩溃 | 看句柄/内存/连接数曲线 |
| 配置漂移 | 改了配置但行为没变 | 确认配置真的被读取（打印生效值） |
| 缓存陈旧 | 改了数据但看到旧结果 | 检查缓存键与失效策略 |

## 用索引加速定位

```bash
node .ai/bin/ai-arch.mjs task "修复：<现象一句话>" --area src/<可疑模块>
node .ai/bin/ai-arch.mjs review --impact src/<可疑文件>
```

任务包会把相关文件与摘要一起给你，避免满仓库搜索。若报错信息里出现了具体函数/字段名，把它作为关键词放进任务描述，命中率更高。

## 反例

- ❌ **猜测式修复**：看到 `null` 报错就加 `if (x) return`，不问为什么是 null。
- ❌ **吞掉错误**：`catch (e) {}` 或把异常改成日志 —— 问题会以更隐蔽的形式回来。
- ❌ **一次改多处**：同时改 5 个地方，即使好了也不知道是哪一处起作用。
- ❌ **不写回归测试**：同一个 bug 三个月后复发。
- ❌ **只修一个入口**：同一个逻辑有 3 个调用方，只修了报错的那个。
- ❌ **修完不更新摘要**：下次 AI 依然按旧的"这个文件没问题"的印象工作。

## 升级为结构性问题的信号

出现以下情况，停止打补丁，改为写 ADR + 重构：

- 同一个缺陷在半年内复发 2 次以上。
- 修复需要"必须先调用 A 再调用 B"的隐式顺序。
- 需要在一个函数里加第 4 个特例分支。
- 修好这里会弄坏那里（耦合过强）。
