# 评审清单

## 一、提交前自查（每次改动，5 分钟）

### 正确性
- [ ] 改动落在任务包声明的"做"范围内；"不做"清单里的东西没被顺手改掉。
- [ ] 边界条件：空输入、极大值、并发、重复调用、失败重试。
- [ ] 错误路径有明确行为（返回错误/降级/抛出），没有静默吞掉。
- [ ] 没有 `ASSUMPTION:` 未标注的猜测（猜的接口/字段/行为必须写进任务包）。

### 可验证性
- [ ] 跑了宪法里的验证命令，并把输出摘要写进任务包第 6 节。
- [ ] 新增行为有测试；无法测试的写明原因与人工验证步骤。
- [ ] 修 bug 时附了能复现原问题的用例（回归测试）。

### 一致性
- [ ] 没有引入宪法"禁止"清单里的东西。
- [ ] 没有引入本规模禁止的设计模式（`ai-arch patterns --level <等级>`）。
- [ ] 命名表达意图；没有 `tmp`、`data2`、`handleThing` 这类名字。
- [ ] 没有为了"将来可能"而增加的抽象层/配置项/插件点（`scope-guard`）。

### 收尾
- [ ] `ai-arch index` 后 `review --drift` 无新增漂移。
- [ ] 按影响矩阵更新了文档与注册表。
- [ ] 任务包第 5/6/7 节填完。

## 二、代码评审（读别人的改动）

按顺序看，不要从第一行看到最后一行：

1. **先看任务包**：范围、验收标准、证据。缺任务包就要求补——否则无法判断改动是否越界。
2. **再看 diff 的"形状"**：改了哪些文件、是否触及模块边界、是否改了公共接口。
3. **然后看数据与契约**：这类改动的 bug 代价最高，也最难在测试里发现。
4. **最后看实现细节**：命名、错误处理、重复代码。

**提问式评审用语**（比断言更有效）：
- "如果 X 为 null，这里会怎样？"
- "这个分支有测试覆盖吗？"
- "这里为什么不复用 Y？"

## 三、架构评审（定期，M 级每季度 / L 级每月 / XL 级双周）

### 输入
```bash
node .ai/bin/ai-arch.mjs scale --gaps
node .ai/bin/ai-arch.mjs review --drift
node .ai/bin/ai-arch.mjs review --decisions
node .ai/bin/ai-arch.mjs task "架构评审：<范围>" --budget 20000
```

### 八问清单

1. **规模变了吗？** 与声明等级是否一致；不一致就写 ADR。
2. **模块边界还在吗？** 有没有出现跨模块直连、循环依赖、绕过公开接口的调用。
3. **有没有"没人敢改"的文件？** （`git log` 看最近改动集中度；单文件反复打补丁是信号）
4. **抽象是否过度？** 有没有只有一个实现的接口、只有一个子类的基类、没人用的配置项。
5. **抽象是否不足？** 同一逻辑复制到 3 处以上、同一 if 判断散落多处。
6. **知识是否落盘？** 最近 5 次任务是否都填了任务包与摘要；有没有只存在于某人脑中的约定。
7. **验证是否有效？** 测试是否真的会在出错时失败（试着改坏一行看测试是否红）；验证命令是否还能跑通。
8. **该删什么？** 死代码、废弃开关、过期 ADR 的状态、不再使用的依赖。

### 产出（必须有痕迹）

- 每个决策一条 ADR（含回退条件）。
- 影响矩阵补充或修正。
- 受影响文件摘要更新。
- 若结论是"架构要改"→ 更新 `docs/architecture/*` 并生成实施任务包。

**只产出两类结论**：立即做（具体到文件与验收条件）、记录待定（写成 Proposed 状态的 ADR）。"以后要注意"不算结论。

## 四、AI 生成代码的额外检查项

| 风险 | 检查方法 |
|---|---|
| 幻觉 API | 对每个外部调用，确认函数/字段真实存在（查类型定义或文档），不确定的标注 `ASSUMPTION:` |
| 过度设计 | 数一下新增的类型/接口/文件数是否与需求复杂度相称 |
| 擅自扩需求 | diff 里是否出现了任务包"不做"清单里的东西 |
| 静默降级 | 有没有 `try { } catch { }` 空捕获，或用假数据糊过未实现的分支 |
| 测试造假 | 断言是否真的能失败（把实现改坏，测试应变红） |
| 格式污染 | 大量无关的格式化/重命名混在同一次改动里 |

## 五、反例

- ❌ 评审时只关注风格（缩进、命名），不看契约与边界条件。
- ❌ 用"LGTM"通过 800 行改动。
- ❌ 架构评审只讨论"要不要引入某技术"，不看当前欠账（`scale --gaps`）。
- ❌ 结论是"以后要注意 XX" —— 这不是可执行结论，应改为规则（影响矩阵）或任务（任务包）。
