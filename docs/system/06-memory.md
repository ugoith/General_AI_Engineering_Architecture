# 记忆架构：知识该放在哪一层

> 回答两个问题：**什么知识写在哪里**、**什么时候写**。放错位置的知识等于不存在——因为它不会在需要的时候被读到。

## 一、五层记忆

| 层 | 位置 | 生命周期 | 读取时机 | 写入时机 |
|---|---|---|---|---|
| **1 会话记忆** | 当前对话 | 一次任务 | 自动 | 不需要（易失） |
| **2 任务记忆** | `.ai/tasks/*.md` | 与任务同寿命（可归档） | 接手同一任务时 | 任务结束时（结果/证据/风险） |
| **3 索引记忆** | `.ai/index/files.json` 的 `digest` | 长期，随文件变化更新 | 每次任务（任务包） | 文件内容变化后 |
| **4 决策记忆** | `.ai/decisions/NNNN-*.md` | 永久 | 触及相关模块/依赖时 | 做出选择时（先写后做） |
| **5 结构记忆** | `docs/`（架构、运行手册） | 长期 | 按路由表 | 结构变化时 |

**判断口诀**：易失的放 1，一次性的放 2，机械可校验的放 3，有取舍的放 4，结构性的放 5。

## 二、放哪里：决策树

```
这条知识是什么？
├─ "这次改了什么、验证了什么"            → 任务包（.ai/tasks/）第 5/6/7 节
├─ "这个文件为何存在、谁依赖它、不能改什么" → 索引 digest（purpose/invariants）
├─ "为什么选了 A 而不是 B，何时该回退"     → ADR（.ai/decisions/）
├─ "系统由哪些模块组成、如何交互"          → docs/architecture/overview.md
├─ "数据长什么样、有哪些字段与约束"        → docs/architecture/data-model.md + .ai/registry.json
├─ "接口/契约长什么样"                    → docs/architecture/interfaces.md + .ai/registry.json
├─ "怎么本地跑起来、常见故障怎么处理"      → docs/runbooks/
├─ "本项目不可协商的红线与验证命令"        → .ai/constitution.md
├─ "怎么完成某类任务（评审/写ADR/排错）"    → .ai/skills/<id>/SKILL.md
└─ "项目通用约定与路由"                   → AGENTS.md（只放指针与硬约束）
```

## 三、什么时候写

| 触发 | 写什么 | 强制程度 |
|---|---|---|
| 改了文件内容 | 更新该文件 digest（`index --stale` → AI 写 → `index --apply`） | **强制**（否则下次 AI 读旧摘要） |
| 做了取舍（依赖/契约/边界/模式） | ADR | **强制**（`decision-trigger` 清单） |
| 加了新模块 | `docs/architecture/overview.md` + 影响矩阵可能新增规则 | 强制 |
| 踩了坑并解决 | digest 的 `invariants`，或 runbook 的"常见故障"一节 | 建议 |
| 发现"改了 A 却忘改 B" | 影响矩阵加一条规则 | **强制**（这是机制修复，不是记性修复） |
| 任务结束 | 任务包第 5/6/7 节（结果/证据/遗留风险） | 强制（完成定义的一部分） |
| 定期评审 | ADR（决策）+ 影响矩阵（规则）+ 摘要（内容） | 强制 |

## 四、什么不要写

- **不要写代码能表达的东西**：函数签名、字段列表、算法步骤——这些读代码就有，写进文档只会造成两份事实。
- **不要写"待补充"的占位文档**：占位文档会污染检索结果，让 AI 浪费时间打开空文件。要么写有用的一行，要么不建这个文件。
- **不要在 `AGENTS.md` 里写知识**：只写指针与硬约束。理由：它是每次会话的固定开销。
- **不要为小项目建大文档**：S 级项目的"结构记忆"就是 README + 一个变更记录。
- **不要把同一知识写两处**：如果必须两处（如 `.ai/registry.json` 与 `data-model.md`），必须指定**哪一份是权威**，另一份只做视图。

## 五、知识的失效与清理

知识会过期，过期知识比没有知识更危险（AI 会照着做）。清理规则：

| 情况 | 动作 |
|---|---|
| 文件被删除 | `index` 自动移除；检查是否有 ADR/文档引用了它（`review --drift` 的 `doc-link-missing`） |
| 文件内容大改 | digest 标记 `stale` → 必须重写（`review --drift` 会报） |
| ADR 的决策被推翻 | **不要删除旧 ADR**；写新 ADR 并把旧的 `Status` 改为 `Superseded by NNNN` |
| 模块被合并/拆分 | 更新 `docs/architecture/overview.md`，并在影响矩阵里保留规则（历史教训仍有价值） |
| 任务包陈旧 | 归档到 `.ai/tasks/archive/`（CLI 不自动做，手动 `git mv` 即可） |
| 索引长期无人维护 | 说明粒度错了或没人执行提交前检查 → 修机制，别写"请记得更新" |

## 六、交接场景（人走 / 换 AI / 隔月回来）

按顺序读：

1. `AGENTS.md` → 骨架与路由（≤150 行）
2. `.ai/constitution.md` → 红线与验证命令
3. `ai-arch doctor` + `ai-arch scale --gaps` → 项目当前健康度与欠账
4. `ai-arch review --decisions` → 历史决策（按时间倒序读最近 5 条）
5. `docs/architecture/overview.md` → 结构
6. `ai-arch task "<要接手的事>"` → 生成针对性上下文包

**这个顺序本身就是设计目标**：接手成本应该是分钟级，而不是"读两天代码"。

## 七、AI 特有的记忆问题

| 问题 | 表现 | 本框架的对策 |
|---|---|---|
| 会话不共享记忆 | 每个新会话从零开始 | 所有知识必须落盘（本框架的存在理由） |
| 上下文窗口有限 | 读太多会丢失早期内容 | 分层预算 + 任务包控制读取量 |
| 倾向于自信地猜 | 猜接口、猜行为 | `ASSUMPTION:` 标记制度（任务包第 7 节）+ 禁止静默降级 |
| 倾向于过度设计 | 简单需求生成多层抽象 | 规模门槛 + 模式 `minLevel` + ADR 前置 |
| 照着过期文档做 | 规范腐化被放大 | digest 的 `hash`/`reviewedHash` 校验 + `review --drift` |
| 重复劳动 | 重读相同文件 | digest 机制（省 40 倍 token） |

## 八、给项目的第一周建议

1. **第 1 天**：`init` 生成骨架 → 填 `.ai/constitution.md`（技术栈、验证命令、红线）→ `index` → 为风险 high 的文件写摘要（通常不超过 10 个）。
2. **第 2–3 天**：把已存在的关键决策**补写**成 ADR（历史决策也值得记录，写"回溯记录"即可）。
3. **第 1 周内**：至少完整走一遍 `task` → 实施 → 填任务包 → `index` → `review --drift` 的循环，让团队/AI 形成习惯。
4. **不要**一次性把所有文件都写摘要：只写 `risk: high` 与被频繁读取的文件，收益最高。
