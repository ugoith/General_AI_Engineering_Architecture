# 设计模式选择：按规模与问题选，不按偏好选

> 对应 CLI：`ai-arch patterns --level M`、`ai-arch patterns --problem 缓存`。机器可读副本：`cli/lib/patterns.mjs` → `PATTERNS`。
> 规模定义见 `02-scales.md`。**先定级，再看这张表。**

## 三条判定原则

1. **模式解决的是"已出现的问题"，不是"可能出现的问题"。** 表里每一项都写明它解决的问题；如果你说不出当前项目正在被这个问题困扰的具体表现（错误日志、返工记录、性能数据），就不该引入。
2. **`minLevel` 是硬门槛。** 低于该规模引入 = 过度设计，视为缺陷而非优点。CLI 的 `--level` 过滤就是干这个的。
3. **`adrRequired` 为"是"的，先写 ADR 再写代码。** ADR 至少要写：备选方案、放弃它们的理由、将来回退的条件。

## 模式矩阵

| 模式 | 解决的问题 | 最低规模 | 代价 | 需要 ADR |
|---|---|---|---|---|
| 显式函数分层（handler → service → repo） | 同一条业务规则被多个入口重复实现，改一处漏一处 | M | 每层一次跳转成本；层职责划分不清时会退化 | 否 |
| 依赖注入（手工传参优先） | 同一对象在多个地方被 new 出来，测试无法替换 | M | 构造函数变长；容器化后启动顺序难追踪 | 否 |
| 仓储接口（Repository） | 业务逻辑里散落 SQL/网络调用，换存储要改遍全局 | M | 一层间接；过度泛化会得到"什么都能存"的接口 | 否 |
| 状态机（显式状态与转移表） | 布尔标志位组合爆炸，非法状态无法排除 | M | 需要维护转移表；状态划分不当会反复重写 | 否 |
| ECS（实体-组件-系统） | 大量同构对象按帧更新，OOP 继承与虚调用成为瓶颈 | M | 思维模型断层、调试困难、与引擎编辑器集成复杂 | 是 |
| 对象池 | 高频创建销毁导致 GC 抖动或分配热点 | M | 生命周期管理与"归还时清理"容易出错 | 否 |
| 数据驱动配置（表/JSON 驱动内容） | 数值与内容调整需要改代码重新构建 | M | 需要 schema 校验与版本迁移 | 否 |
| 适配器/防腐层（Anti-Corruption Layer） | 外部系统的数据模型与术语渗入核心领域 | M | 一层转换代码 | 否 |
| 特性开关（Feature Flag） | 未完成功能需要合并但不可见，或需要灰度 | M | 开关会累积成债务，必须有清理时限 | 否 |
| 事件/消息解耦（进程内） | 一个动作要触发多个互不相关的副作用，直接调用导致循环依赖 | L | 调用链不可见、调试困难、顺序不确定 | 是 |
| CQRS / 读写分离 | 读写负载特征差异极大，且写模型的约束拖慢读路径 | L | 最终一致性、重复代码、同步管道 | 是 |
| 插件/扩展点（SPI） | 同一套核心要支持多种外部实现，且实现方与核心分开发布 | L | 版本兼容矩阵、加载失败处理、安全边界 | 是 |
| 契约优先（先定接口/数据结构再实现） | 多方并行开发时接口反复变更，返工成本高 | L | 前期投入；契约变更需要流程 | 是 |
| 分层缓存 | 重复计算或远程调用成本高，且延迟不可接受 | L | 失效策略是 bug 的主要来源 | 是 |
| DDD 战术模式（聚合/值对象/领域事件） | 业务规则复杂且频繁变化，需要显式表达不变式 | L | 建模成本高；用错地方会得到贫血包装 | 是 |

## 常见误判与纠正

| 常见做法 | 为什么错 | 应该怎么做 |
|---|---|---|
| "以后可能要支持多个数据库，所以现在就加仓储接口" | 用未来的假设换现在的复杂度；真实需求出现时接口往往完全不同 | 先用具体实现，把 SQL 集中在一个文件里（成本几乎为零的"准仓储"） |
| "用事件总线解耦，模块之间就不用互相知道了" | 调用链变不可见，排错时间指数上升 | M 级以内用显式调用 + 一处汇总函数；真的需要时再上事件并写 ADR |
| "小项目也要用 DI 容器，方便测试" | 手工传参已能满足测试替换；容器带来启动顺序与循环依赖问题 | 构造函数传参；测试直接构造真实对象 |
| "游戏要高性能，直接上 ECS" | 没有 profiler 数据时，ECS 只是把简单问题复杂化 | 先用普通对象 + 列表实现，用 profiler 证明瓶颈后再迁移 |
| "先把抽象层搭好，业务后面填" | 抽象层在没有第二个实现时无法验证，几乎必然返工 | 有一个具体实现后再抽接口（Rule of Three） |
| "为了统一，所有模块都要经过统一的服务层" | 为一致性引入的层会成为所有改动的必经之路 | 只对确实需要共享规则的路径加层 |

## 反模式清单（按当前规模动态给出）

```bash
node .ai/bin/ai-arch.mjs patterns --level S   # 会输出 S 级的禁止清单
```

S 级禁止：DI 容器、事件总线、仓储层/分层架构、CQRS、微服务、自研框架或 RPC、多级缓存、插件系统、"抽象工厂 + 策略族"组合。

M 级新增禁止：CQRS、微服务、多级缓存、自研序列化、无 ADR 的跨模块重构。

L 级新增禁止：无 ADR 的跨模块重构、隐式全局状态、绕过契约层的跨模块直连。

XL 级新增禁止：单体式共享库、无版本的契约变更、跨领域的直接数据库访问。

**判定方法**：如果一个改动让 README 里的"如何运行"步骤变多、让一个新人的上手路径变长、或让排错需要跨 3 个以上文件，而当前规模又在禁止清单里，就说明引入了过度设计。

## 对 AI 的额外要求

AI 有"展示能力"的倾向：面对简单需求也容易生成接口 + 工厂 + 策略 + 事件。本框架对此的约束是：

1. 生成代码前先 `ai-arch patterns --level <当前等级>`，把禁止清单读一遍。
2. 想引入表中任何 `adrRequired: true` 的模式时，**先写 ADR，等确认后再实现**。
3. 引入 `minLevel` 高于当前等级的模式时，必须在任务包里写明"为什么当前规模也需要它"，并升级规模等级或放弃。
