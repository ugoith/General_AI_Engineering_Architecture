# 上下文纪律：如何让 AI 不重复读文件

> 这是本框架解决你原始痛点的核心机制。对应 CLI：`ai-arch index`、`ai-arch task`、`ai-arch review --drift`。
> "AI 每次都要重读相同文件"的根因不是 AI 笨，而是**没有机制记录"上次读到了什么"**。本文定义这个机制。

## 一、四层上下文与预算

| 层 | 文件 | 何时读 | 上限 | 实测 token（`node scripts/measure-budget.mjs`） |
|---|---|---|---|---|
| **L0 入口** | `AGENTS.md` | 每会话（工具自动加载） | ≤ 150 行 / ≤ 2500 token | 软件类 ~1670；游戏类 ~1940–2390 |
| **L1 宪法** | `.ai/constitution.md` | 每会话 | ≤ 150 行 / ≤ 1800 token | ~1240（软件）–1650（游戏） |
| **L2 索引** | `.ai/index/files.json`、`.ai/registry.json`、`.ai/index/impact-map.json`、`.ai/rules.json`、`.ai/project-facts.json`、资产索引 | 接到任务后按需查询 | 每次查询取所需条目 | ~200–2900 |
| **L3 源码** | 具体文件 | 仅当任务包列出，或摘要不足 | 由任务包预算控制 | 变化 |

任务包默认预算：**40000 token**（`--budget` 可调；超过的部分会被列入"丢弃"清单而不是静默省略）。

**行数是代理指标，真约束是 token**：游戏类 `AGENTS.md` 实测 110–132 行（内联共享片段 + 引擎专项硬约束 + 引擎必读项与验证命令），项目再接入自身既有的规范体系时会多加几行，因此行数上限取 150。阈值应当约束**真问题**（每会话固定成本），而不是制造噪音。完整理由（含 2100 → 2500 的调整原因）见 `cli/lib/limits.mjs`。

**固定成本的实际量级**：L0 + L1 ≈ 2900 token（软件类）到 4000 token（game-unreal：C++/蓝图边界 + GC/模块/资产纪律 + 编译、测试、打包三条命令）。这是每个任务都要付的钱，所以它的上限由 `cli/lib/limits.mjs` 强制（`AGENTS_TOKEN_BUDGET` / `CONTEXT_TOKEN_BUDGETS`），`review --drift` 与 `doctor` 都会检查。

**为什么 L0 能到 2000 token**：`AGENTS.md` 里内联了共享片段（上下文纪律、完成定义、范围守卫），游戏类还内联了引擎专项硬约束——因为片段不做变量替换、必须自洽。这部分固定成本换来的是"生成即可用"。要压缩时应砍"项目定位/指针"类内容（那些已在文档里），**不要砍硬约束与引擎专项**。

## 一.5 什么不进上下文

框架快照不是项目内容，**不进索引、不写摘要、不进任务读取清单**：

| 路径 | 内容 | 为什么排除 |
|---|---|---|
| `.ai/framework/docs/` | 框架规范快照 | 描述框架本身，不是本项目 |
| `.ai/framework/templates/` | 模板快照（供项目内 `init`/`upgrade` 用） | 同上，且体量大 |
| `.ai/bin/`、`.ai/lib/` | CLI 工具链副本 | 只读框架资产 |
| `.ai/cache/` | 摘要请求等临时文件 | 本地临时数据（已被 `.gitignore` 忽略） |

实测影响：一个刚 `init` 的空项目，若不排除框架快照，索引是 149 个文件（其中项目文件只有 9 个），任务包会被框架自身文件占满；排除后索引只剩项目文件 + 5 个上下文文件。

**但下面这些 `.ai/` 文件必须进索引**（这是一条很容易写错的边界）：

| 路径 | 为什么必须进索引 |
|---|---|
| `.ai/constitution.md` | L1，每会话必读。它的 hash 要进任务包，收尾时才能对账"这次是不是动了红线" |
| `.ai/registry.json` | 契约层数据；不进索引就无法对账"注册表自己改没改" |
| `.ai/index/impact-map.json` | 影响矩阵；改它等于改了变更协议 |
| `.ai/index/README.md`、`.ai/skills/README.md` | 索引体系与任务知识的说明书 |
| `.ai/index/` 下的索引体系文档（如 UE 的 `.ai/index/asset-index.md`） | 模板包声明为必读的资产/域索引；不进索引就等于"必读项没有 hash、收尾无法对账" |
| `.ai/rules.json`、`.ai/project-facts.json` | 任务包按它们的 hash 判定"规则/事实是否变过" |

判定线是：**这个文件参与"判定"，还是只参与"存证"**。参与判定的（宪法、规则、事实、契约、影响矩阵、索引说明）必须进索引，
否则它们改了没有任何机制能发现——早期实现把整个 `.ai/` 一刀切排除，结果"每会话必读的文件"反而成了唯一没有对账的文件。
只参与存证的（框架快照、CLI 副本、任务包、技能副本、ADR）不进索引。
实现见 `cli/lib/indexer.mjs` 的 `AI_INDEXED_PATHS` / `isFrameworkSnapshot()`；`.ai/` 的行数单独记为 `summary.contextLoc`，不混进 `totalLoc`（规模等级判定看的是源行数，见 `docs/system/02-scales.md`）。

**总原则**：L0 + L1 是**固定成本**，必须压在 `cli/lib/limits.mjs` 的上限内（`AGENTS.md` ≤ 2500、`.ai/constitution.md` ≤ 1800）；L2 是**按需查询**，不要整份读；L3 是**最贵的**，只读任务包要求的部分。

> 常见错误：把架构说明、编码规范全文塞进 `AGENTS.md`。这会让每个任务都多付一次费用，而且模型会顺着这些指令做超出必要的探索。知识应放在 `docs/`，由路由表指向。

## 二、文件摘要（digest）机制 —— 省上下文的关键

`.ai/index/files.json` 里每个文件有两条信息：

| 字段 | 含义 | 谁生成 |
|---|---|---|
| `hash` | 文件内容的 SHA-256 指纹（前 10 位即可比对） | CLI 自动 |
| `digest` | 语义摘要：`purpose`（为何存在）、`exports`（对外接口）、`invariants`（必须保持的不变式）、`risk`、`tags` | **AI 写**，CLI 校验并回填 |
| `digest.reviewedHash` | 这条摘要对应的内容版本 | CLI 自动记录 |

**判定规则（必须遵守）**：

```
hash 未变 且 digest 存在  →  只读 digest，不要打开源码
hash 已变 或 digest 缺失  →  必须读源码；读完后重写 digest
```

这条规则把"每次重读"变成"只在变化时读"。实测（`node scripts/measure-digest.mjs`）：一个 320 行的 TypeScript 文件，整读 ≈ 3550 token，只读摘要 ≈ 52 token —— **相差约 68 倍**。文件越大差距越大，且摘要长度基本恒定。

### 摘要由谁写、什么时候写

摘要必须是语义理解，CLI 不能自动生成。工作流：

```bash
# 1. 生成"待写摘要"清单（含每个文件的 hash、行数、依赖数、旧摘要）
node .ai/bin/ai-arch.mjs index --stale --json > .ai/cache/digest-request.json

# 2. 把该文件与清单里列出的源码交给 AI，要求它只输出 JSON 数组：
#    [{ "path": "...", "reviewedHash": "<原样回填>", "purpose": "...", "exports": [...],
#       "invariants": [...], "risk": "low|medium|high", "tags": [...] }]

# 3. 把 AI 产出的 JSON 存为文件后回填（会校验 hash 是否与当前内容一致）
node .ai/bin/ai-arch.mjs index --apply .ai/cache/digests.json
```

**安全设计**：`--apply` 会拒绝 hash 不匹配的条目（说明文件在阅读后又变了，摘要已失效）。这防止"AI 凭旧印象写摘要"污染索引。

**摘要写作要求**：

- `purpose` ≤ 200 字，回答"这个文件为什么存在、谁依赖它"，**不要复述代码**。
- `invariants` 写"改这里时必须保持什么"（例如"玩家血量不得为负""该函数不得抛异常"）——这是给未来 AI 的红线。
- `exports` 只写对外真正可见的符号。
- 不确定就留空。**编造摘要比没有摘要更危险**，因为它会让后续 AI 跳过源码。

## 三、任务包（task pack）—— 开工前先拿清单

```bash
node .ai/bin/ai-arch.mjs task "给登录接口加 token 刷新，失败时回落到重新登录"
```

生成 `.ai/tasks/<日期>-<slug>.md`，内容包含：

1. **索引健康度**（有多少文件还没摘要 —— 没摘要的文件会被判定为"必须读源码"，成本高）。
2. **必读**（固定成本，附 token 估算）。其中 `AGENTS.md`（L0）与 `.ai/constitution.md`（L1）每次都读；
   `.ai/index/README.md` 只在**本项目第一次任务**或**索引 schemaVersion 变化**时列入——框架不为"只需读一次"的说明书每次都收费，
   跳过时会在任务包里写明"本次为什么不读它"（否则会被误读成框架漏了）。
   模板包还可以声明自己类型的必读项（`alwaysRead`，如游戏类的资产索引）。
3. **读取清单**：每个文件给出 `decision`：
   - `read-source`：hash 变了或没摘要 → 读源码
   - `read-digest`：hash 未变 → **只读摘要，不要打开源码**
   并给出入选原因（命中了哪些关键词 / 是依赖方）、hash、风险、被依赖数、token 估算。
4. **已知摘要正文**：直接可用，不需要再读源码。
5. **因预算丢弃的文件**：明确告知"这些相关但没预算"，让 AI 不要偷偷去读。
6. **范围 / 验收标准 / 结果 / 证据 / 遗留风险**：任务包同时是**交接文档**，填完就是一次可追溯的工作记录。
7. **收尾对账基准**：任务包里每个文件的 `hash` 就是收尾时的比对基准 —— `ai-arch review --task` 重新 hash 这些文件，
   回答四个问题：当时让我只读摘要的文件是不是已经变了（**前提失效**）、索引/摘要补了没有、契约注册表同步了没有、任务包自己三节填了没有。
   这条链路不需要全树扫描，成本只与任务包长度有关。

### 预算控制

```bash
node .ai/bin/ai-arch.mjs task "..." --budget 40000 --max-files 25 --area src/auth --expand 1
```

| 参数 | 默认 | 作用 |
|---|---|---|
| `--budget` | 40000 | token 上限；超出的文件被列入"丢弃"而不是静默省略 |
| `--max-files` | 25 | 清单长度上限 |
| `--area` | 无 | 限定目录，索引很大（>400 文件）时必须用 |
| `--expand` | 1 | 依赖邻居扩展深度（顺着 `imports`/`importedBy`） |
| `--changed` | 无 | 显式指定本次变更文件，必进清单 |

**预算超了怎么办**：先缩小任务范围（一个任务包只解决一件事），而不是提高预算硬读。任务包里的"丢弃"清单就是给这个判断用的。

## 四、读完之后：把知识写回索引

任务结束时（属于"完成定义"的一部分）：

```bash
node .ai/bin/ai-arch.mjs review --task    # 0. 闭环自查：计划 vs 实际、该补什么、该跑哪些测试（只 hash 任务包列过的文件）
node .ai/bin/ai-arch.mjs index            # 1. 更新 hash、行数、依赖关系
node .ai/bin/ai-arch.mjs index --stale    # 2. 看待写摘要（第 0 步会告诉你哪几个是本次改动造成的）
node .ai/bin/ai-arch.mjs review --drift   # 3. 确认没有遗留漂移
```

第 0 步是**机械化收尾**：它不要求你记得"这次改了什么"，而是拿任务包记录的 hash 与实际内容对账。
判定不了的不做——它不会声称"测试跑过了"，只会列出"应运行什么"。

这次读到的**非显然知识**（为什么这么设计、哪些坑不能踩）应该写进：

- `digest.invariants` —— 如果它是"改这个文件必须注意的约束"；
- `.ai/decisions/` 的 ADR —— 如果它是一个选择；
- `docs/` 的架构文档 —— 如果它是结构性知识。

**判断标准**：如果下一个人/下一次 AI 会因为不知道这件事而犯错，就必须写下来；否则不要写（文档也要花上下文预算）。

## 五、任务包对比：有机制 vs 没机制

| 场景 | 没有机制 | 有机制 |
|---|---|---|
| 修改一个已改过两次的模块 | 重新搜索、读 10–20 个文件 | 读 L0/L1（~2000 token）+ 3 个摘要（~200 token）+ 2 个变更文件源码 |
| 判断改动影响面 | 靠模型猜测或全局搜索 | `review --impact <file>` 给出依赖方与应跑测试 |
| 新人/新 AI 接手 | 全靠问人 | 任务包 + 索引 + ADR 就是交接材料 |
| 规范是否过期 | 无法判断 | `review --drift` 直接列出 |

## 六、失败模式与对策

| 现象 | 根因 | 对策 |
|---|---|---|
| AI 仍然整仓库搜索 | 任务包没给 / 没读 | 把"先要任务包"写进 `AGENTS.md` 的第一条硬约束（模板已含） |
| 摘要写了但没人信 | 摘要编造、与代码不符 | `--apply` 的 hash 校验 + 任务包里显示 `reviewedHash` |
| 索引很大导致任务包噪音多 | 单仓巨库 | 用 `--area` 限定；XT 级项目考虑按域拆分多个 `.ai/` 域索引 |
| 索引长期不更新 | 没有触发时机 | 提交前检查（`review --drift`）+ 提交钩子建议 |
| 摘要比源码还长 | 写成了代码复述 | 硬性要求 `purpose` ≤ 200 字；摘要只写"为何存在/谁依赖/不能变什么" |

## 七、Token 估算说明

CLI 用字符启发式：ASCII ≈ 4 字符/token，CJK ≈ 0.6 token/字符；源码按 9 token/行估算。
误差约 ±20%，**足够用于预算决策，不适合用于计费**。详见 `docs/04-design-notes.md` 的"尚未验证的假设"。
