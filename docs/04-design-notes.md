# 设计说明：为什么是这些机制，以及我们拒绝了什么

> 这份文档解释**取舍**，不定义规则。规则在 `docs/system/`。当你想改规则时，先读这里，避免把已经否决的方案重新引进来。

## 1. 根问题：AI 协作的成本结构变了

传统工程规范优化的目标是"新人上手成本"与"长期可维护性"。AI 参与后，成本结构变成：

| 成本项 | 传统工程 | AI 协作 |
|---|---|---|
| 阅读代码 | 一次性、人脑有长期记忆 | **每会话重复付费**，上下文窗口是硬上限 |
| 写代码 | 主要成本 | 边际成本大幅下降 |
| 保持一致 | 靠人记忆与评审 | 靠**可检索的显式规范**；模型默认行为会覆盖隐式约定 |
| 规范腐化 | 慢（季度级） | **快（天级）**：模型会照着过期文档生成过时代码 |

因此本框架的优化目标不是"文档更全"，而是**单位上下文的信息密度**与**规范的自我纠错能力**。这解释了几个看起来反直觉的设计。

## 2. 为什么 AGENTS.md 必须短

生态已有共识：`AGENTS.md` 是**会话启动时无条件加载**的文件（见 [AGENTS.md 标准](https://agents.md)、[agents-md 规范说明](https://raw.githubusercontent.com/agentpatterns-ai/website/refs/heads/main/standards/agents-md.md)）。
无条件加载 = 每个任务的固定税。已有评测指出，冗长的上下文文件会显著抬高推理成本，因为模型会顺着指令做超出必要的探索。

**拒绝的方案**：把架构说明、编码规范全文写进 `AGENTS.md`。
**采用的方案**：`AGENTS.md` ≤ 120 行，只做三件事——硬约束、路由表、提交前检查。知识放 `docs/`，按需读取。

## 3. 为什么需要"文件摘要"而不是"每次都读源码"

用户的原始痛点：*"我这次读了很多文件、写了代码、跑通测试；下次还要再读一遍吗？"*

答案取决于**文件是否变化**，而这件事可以廉价判定：存 `hash`。

- hash 未变 → 只读摘要（约 30–80 token/文件），任务包会附上 hash。
- hash 变化 → 只读该文件 + 依赖它的摘要（影响面由索引的 `imports`/`importedBy` 反查）。

**拒绝的方案**：用向量库/RAG 索引代码库。
理由：引入外部依赖与运维成本，且检索结果不可解释、无法审计"为什么读了这个文件"。本框架要求读什么文件是**可复现、可 diff、可提交**的——任务包是一份落盘的 JSON，人和 AI 都能审。

**代价**：摘要需要有人（通常是 AI）在变更后重写。这正是 `ai-arch index --stale` 与提交前检查存在的原因；我们选择把成本显式化，而不是隐藏在一次不确定的检索里。

## 4. 为什么规模分级先于设计模式

*"小型项目也许用不到高级的设计模式"* ——这条直觉是对的，而且必须写成硬规则，否则模型会倾向"展示能力"。

因此 `docs/system/02-scales.md` 给出带阈值的 S/M/L/XL 分级，`docs/system/03-pattern-selection.md` 给出"什么规模才允许什么模式"的矩阵，并明确**禁止清单**（如 S 级项目禁止引入 DI 容器、领域事件总线、CQRS）。
**拒绝的方案**：一份"最佳实践大全"，让使用者自行取舍。
理由：模型与新人都会过度应用；把禁止项写死，比写"请酌情"有效。

## 5. 为什么规范要"随变更演进"而不是"一次写对"

*"随着项目的推进与用户的要求，索引和规范一定是要进行更新的。"*

规范腐化的根因不是没人写，而是**没有触发时机**。本框架把更新挂在三个已有的动作上：

1. **变更时**：`09-change-protocol.md` 的影响矩阵（改了 A 就必须同步 B/C）。
2. **提交前**：`review --drift` 机械检测（hash 漂移、决策缺失、链接断裂）。
3. **定期**：`05-lifecycle.md` 的评审触发条件（规模升级、里程碑、连续 N 次补丁式修改…）。

**拒绝的方案**：靠"定期大扫除"。
理由：没有触发条件的定期动作一定会被推迟到忘记。

## 6. 为什么交付形态是"复制式脚手架"而不是 submodule

- 项目必须能**自由改写**框架文件：真实的项目总会有例外，强绑定会逼用户绕过框架。
- 框架升级不该污染项目的 git 历史；`upgrade` 按"框架文件是否被本地改动过"三态处理（覆盖 / 保留 / 提示合并）。
- 复制式对非 git 团队、对导出 zip 交付、对 AI 直接读文件都最友好。

代价：升级需要跑命令。我们接受这个代价，并把 `upgrade --dry-run` 做成默认安全行为。

## 7. 为什么核心不放 `.claude/`、`.workbuddy/` 这类 agent 目录

这是一个被反复提出的诉求（"希望目录简洁、直接放进 agent 自己的文件夹"）。我们**拒绝了把核心放进去**，但接受了它的目标，做法是"核心 + 薄指针"：

| 方案 | 后果 |
|---|---|
| 核心放 `.claude/`（或 `.workbuddy/` 等） | ① 项目**绑定单一工具**：换 AI 工具时索引、任务包、ADR 全部要搬家，而这套架构最有价值的部分恰恰是跨会话、跨工具的记忆；② 破坏 **`AGENTS.md` 的仓库根发现约定**（[agents.md](https://agents.md)），多数工具会话启动时只找根目录，放进子目录后不会被自动加载；③ 这些目录常含**每机私有**内容（如被全局 gitignore 的 `.claude/settings.local.json`），团队共享的项目记忆会因此丢失 |
| 核心放 `.ai/` + agent 目录放指针（采用） | 工具无关、可入库、可 diff；每个 agent 目录里只有一个几行的指针文件，**可随时删除**；目录依然简洁 |

指针文件的四条约束（实现见 `cli/lib/install.mjs`）：只在**已存在**的 agent 根目录下写（不凭空造目录）、绝不覆盖项目原有同名文件、带统一标记表明可删、内容只有"去读 `AGENTS.md` 与 `.ai/`"而不复制知识。

**代价**：多了一个 `.ai/` 目录。**接受的代价**：若某个工具确实只认自己的目录且不读根 `AGENTS.md`，我们仍为它写指针——但知识始终只有一份。

## 8. 明确拒绝的东西（反模式，勿重新引入）

| 被拒绝的做法 | 原因 |
|---|---|
| 用向量库做代码检索 | 不可解释、不可 diff、引入依赖 |
| 让 AI 生成"完整详细文档" | 与上下文预算直接冲突；文档只在被读取时才产生价值 |
| 每个项目一套自动生成的巨型规范 | 规范正文应来自框架，项目只写**差异**（宪法里的项目专属部分） |
| 用 submodule 挂载框架 | 削弱项目自治，升级路径脆弱 |
| 在 `AGENTS.md` 内联教程 | 抬高每个任务的固定成本 |
| 强制所有项目同等级流程 | 小项目流程过重会被直接抛弃，反而零收益 |
| 让 CLI 自动改写源码/自动提交 | 不可审计；CLI 只做生成、检测、报告，改动由人和 AI 显式完成 |
| 把核心知识放进 `.claude/`、`.workbuddy/` 等 agent 私有目录 | 破坏工具无关性与 `AGENTS.md` 发现约定，且这些目录常是每机私有（见第 7 节） |
| 提供"一个按钮全自动改项目"的模式 | 接入必须可预演（`--dry-run`）、可逐条审阅、可整体回退 |

## 8. 尚未验证的假设（欢迎用真实项目证伪）

1. 摘要粒度以"单文件"为默认是对的；超大类（XL）可能需要"目录级摘要 + 文件级仅高风险"。
2. token 估算用字符启发式（英文/代码 ≈ 4 字符/token，CJK ≈ 0.6 token/字符）误差在 ±20%，足以做预算判断，但不适合计费。
3. "任务包"的自动组装能覆盖 80% 的开工场景；剩余 20%（跨模块重构）仍需人工补文件——所以任务包允许手工追加条目。
4. S 级项目的轻量流程是否会被 AI 主动遵守，需要在真实小项目上观察。

发现反例请开 issue 并附上项目规模与实测数据。
