# AI 工程框架调研报告

面向「通用 AI 工程架构」的定位、对比与优化空间

---

## 一、结论先说

1. **这类框架已经形成赛道，但没有任何一个在"过程完整性"上全面覆盖。** 2026 年 6 月的 arXiv 论文《From Prompt to Process》用六维分类学（规格、上下文、角色、执行、验证、可移植性）评估了六个主流框架，明确结论：**没有框架在六维上都强，过程深度与跨 agent 可移植性之间存在结构性取舍**。这对我们是好消息——它说明空位是结构性的，不是我们没找到。
2. **最拥挤的是"规格"维度，最空的是"上下文治理"。** 六个框架几乎都在做"让人把需求写成可审查的产物"；但没有一个把**读什么、读多少、何时可以不读**做成一等公民。而这恰好是我们框架的核心（确定性索引 + hash 增量 + 预算化任务包）。
3. **可移植性是普遍短板，也是我们最大的差异点。** 论文把"跨 agent 可移植"列为独立维度，并指出多数框架在此薄弱（如 GSD 强耦合单一 agent）。我们已经做到**一份源产出 7 种分发形态**，覆盖 Claude Code、Cursor、Copilot、Gemini CLI、DeepSeek Harness、Codex 等，并且核心知识存放在工具中立的 `.ai/`。
4. **论文列出的五类反复出现的风险中，我们已机械化处理了四类**（见第五章对照表），剩下的"社区扩展脆弱"与"缺基准"是行业性问题，不是单框架能解决的。
5. **可优化空间集中在三处**：① 我们的"验证"维度偏弱（只有漂移检测，缺设计与实现的一致性检查）；② "角色"维度刻意留白（这是权衡，但需要显式说明）；③ 缺可复现的**基准与中间质量指标**——论文与行业都在呼吁，谁先做出来谁就有话语权。

## 三、赛道全景：六类做法

论文把候选按"进攻路径"归类，我沿用并补充标准类：

### 3.1 规格驱动开发（SDD）——最拥挤的一类

| 框架 | 做法 | 采用量（2026-05 快照） |
|---|---|---|
| GitHub Spec Kit | 把规格当作中心产物：constitution → specification → plan → tasks → implement，配套 clarify/analyze/checklist 命令 | 约 10.7 万 star |
| OpenSpec | 轻量 SDD：把意图收敛到单一规格 + 可追溯的变更提案，降低流程摩擦 | 约 5.1 万 star |
| BMAD Method | 按阶段组织（分析、规划、方案、实现），配专业角色 agent 与工作流 | 约 4.8 万 star |
| GSD（Get Shit Done） | 把**上下文装配**当作显式工程任务：先决定 agent 读什么、按什么顺序读 | 约 6.4 万 star |
| Spec Kitty | 用 git worktree 隔离执行，合并前强制评审与验收 | 约 0.13 万 star |

### 3.2 反向工程：从遗留代码恢复规格

**Reversa**：与其他框架方向相反——不从新产品出发，而是从既有系统反推可操作的规格，并标注置信度与缺口。这解决的是"接手遗留系统"的真实场景，是主流 SDD 指南普遍缺失的一路。

### 3.3 上下文与索引类（与我们最接近）

| 工作 | 做法 | 与我们的关系 |
|---|---|---|
| GSD | 上下文装配显式化：决定读什么、什么顺序 | 思路一致，但它的实现强耦合单一 agent，可移植性弱 |
| CodeDNA | 主张**在源码内嵌注释**（in-source annotation）作为 LLM 导航的确定性锚点 | **路线不同**：它把导航信息写进源码（侵入式、需改代码），我们放在 `.ai/index/`（非侵入式、可独立演进） |
| Graph-RAG for codebases | 用 AST 派生图做检索 | **路线不同**：它仍是"检索"，不可 diff、不可审计；我们要求读取清单可复现 |

### 3.4 标准与约定（不是框架，但决定生态）

| 标准 | 作用 | 我们的采用情况 |
|---|---|---|
| AGENTS.md | 仓库根的 agent 入口，跨工具自动加载 | 已采用，并强制 ≤150 行（"指针不是百科"） |
| Agent Skills（SKILL.md） | 任务知识打包标准，`name`/`description`/`whenToUse` | 已采用，7 个 skill，并在校验器里强制字段名 |
| MCP | agent 与外部能力的协议 | 已用于 DSH 插件（只读工具），并在 UE 场景记录其边界 |

## 四、六维对照：我们与主流框架的差异

论文的六维分类学（每个维度的"引导问题"见其 Table 4）。下表是**维度级对照**，不是逐框架打分（那需要论文的完整评分表；此处只标注我们与主流做法的结构性差异）：

| 维度 | 主流框架的普遍做法 | 我们的做法 | 差异性质 |
|---|---|---|---|
| 规格 | 强项：把需求变成可审查的产物（规格、PRD、计划、任务、验收标准） | 弱项：只提供**宪法 + 影响矩阵 + 规则集**，不管理产品需求 | **我们不做这一层**，设计上交给 SDD 类工具 |
| 上下文 | 靠文档与约定；GSD 显式化；CodeDNA 走源码内嵌 | **一等公民**：文件级 hash + 语义摘要 + 预算化任务包 + 规则/事实随包下发 | **我们的强项，也是最空的位置** |
| 角色 | BMAD 最显式（分析/产品/架构/开发/UX）；Spec Kitty 把评审与验收做成流程角色 | **刻意留白**：不预设角色，只提供"何时必须停下来问用户"的对齐触发条件 | 权衡：留白换来可移植，但需在文档中显式说明 |
| 执行 | Spec Kitty 用 worktree 隔离执行；多数框架只给命令流程 | **刻意不执行**：CLI 只生成、检测、报告；不改源码、不自动提交 | 权衡：可审计优先 |
| 验证 | Spec Kit 有 analyze/checklist；BMAD 有就绪检查与评审；Reversa 标注置信度与缺口 | 机械漂移检测（摘要过期、文档断链、决策缺失、预算超限）+ 完成定义以"真实命令输出"为准 | **尚不完整**：缺"设计意图 vs 实现"的一致性检查 |
| 可移植性 | 普遍薄弱：多数框架依赖特定 agent 或自有仓库约定 | 工具中立目录 + 一份源产出 7 种分发形态 + 单文件离线版 | **我们的强项** |

**一句话定位**：
> 主流框架在解决"**把需求变成可审查的产物**"；我们在解决"**让 agent 不要重复读、不要用过期前提、不要把约束说出来就忘掉**"。两者互补，重叠面很小。

## 五、论文列出的五类风险，我们的处理情况

论文在讨论中列出反复出现的风险。逐条对照（这是本报告最实用的部分）：

| 论文指出的风险 | 我们的机制 | 状态 |
|---|---|---|
| 规格与代码漂移 | 文件级 hash + 摘要 `reviewedHash` 校验：内容变了摘要会被拒绝、`review --drift` 报 `digest-stale` | 已机械化 |
| 过度信任生成产物 | 完成定义要求贴**真实命令输出**；禁止"应该没问题"；`index --apply` 拒绝 hash 不匹配的摘要 | 已机械化 |
| 社区扩展脆弱 | 我们是零依赖、无插件生态的设计（反向取舍） | 天然规避，但也因此没有生态红利 |
| 平台依赖 | 核心在工具中立 `.ai/`；7 种分发形态；单文件离线版 | 已解决 |
| 缺完整过程的基准 | **尚未解决**（见第六章） | 待办 |

## 六、优化空间（按性价比排序）

### 6.1 值得做：补"验证"维度的缺口（高性价比）

现状：我们能检测"文档/摘要与代码不一致"，但检测不了"**设计意图与实现不一致**"。

候选做法（按成本从低到高）：

1. **不变量断言**：`registry.json` 里每个关键实体已有 `invariants` 字段，目前只作为信息展示。可让 `review` 检查"有 invariants 的实体是否至少被一条测试引用"。成本低，直接复用现有数据。
2. **契约测试挂钩**：影响矩阵里 `api-contract-change` 已要求"同步契约测试"，但只提示不校验。可加一条检查：改动契约文件时，若配套契约测试未变，报 warn。
3. **设计意图抽查**：由 `task` 生成的任务包要求填写"验收标准"，收尾时校验是否有对应证据。这需要把任务包从"供人填"升级为"可校验的结构化产物"。

**判断**：第 1、2 项成本低、收益明确，建议做；第 3 项会加重流程，M 级以下项目应保持可选。

### 6.2 值得做：把"角色留白"变成显式设计（低成本，防误解）

我们刻意不预设角色（分析师/架构师/开发者），这是为了可移植。但**不说清楚就会被当成缺失**。建议在框架文档里显式写明：
- 为什么不预设角色（预设角色会绑定 agent 的编排方式，破坏可移植性）
- 需要角色的团队应当怎么做（把它做成项目级 skill 或 rules，而不是框架内置）

**判断**：纯文档工作，几乎零成本，能显著改善定位清晰度。

### 6.3 值得做：建立可复现的基准（高成本，高价值）

论文把"缺完整过程的基准"列为全行业空白，并点名几类**中间质量指标**（而非只看最终代码质量）：上下文治理、安装安全、可复现性。

我们能做的最小版本：
- **上下文效率基准**：给定仓库 + 一组任务，测量"任务包估算 token vs 实际读取量"、"摘要覆盖率 vs 重读次数"。我们已有 `measure-digest.mjs`（实测 68 倍）作为雏形。
- **漂移检出率基准**：注入已知的文档/摘要漂移，测 `review --drift` 的召回率。
- **跨 agent 一致性基准**：同一任务在 N 个 agent 上跑，比较**读取清单的重合度**（清单是我们产出的，因此可比较）。

**判断**：这是把项目从"工程工具"提升为"可被引用的工作"的路径，但工作量大，建议先做第一个（上下文效率）。

### 6.4 需要权衡：是否补"规格"维度

论文显示"规格"维度已经很拥挤（Spec Kit 10 万 star 量级）。**不建议自建规格管理**，建议：

- 提供**与 SDD 工具的对接约定**：把 SDD 产出的规格目录纳入影响矩阵的 `mustUpdate`，让规格变更触发我们的同步检查；
- 在 `task` 里支持"从规格文件生成任务包"（读取规格 → 提炼关键词 → 走现有打分流程）。成本低，且把两个生态接起来。

### 6.5 明确不做

| 不做 | 理由 |
|---|---|
| 向量库/嵌入检索 | 不可解释、不可 diff，与"读取清单可复现"直接冲突 |
| 源码内嵌导航注释（CodeDNA 路线） | 侵入式：要改业务代码；且需要团队接受新注释规范。我们选非侵入式 `.ai/` |
| 自建多 agent 编排/角色系统 | 会绑定 agent 的运行方式，破坏可移植性；主流已有多个方案 |
| 自建规格/PRD 管理 | 赛道拥挤，重复投入 |

## 七、局限与未验证事项

1. **框架效果缺独立评测**：论文明确指出，六个被评框架**都没有独立学术评测**（其 Table 2 逐个标注 "No"）。本报告对它们的描述同样来自官方文档，属 `[文档]` 强度。
2. **采用量快照会过期**：star 数与活跃度取自论文 2026 年 5 月的快照，只用于说明量级。
3. **六维对照是维度级**：我们未对六个框架逐条打分，因此不能声称"我们在某维度优于某框架"；能声称的是"该维度上做法的结构性差异"。
4. **我们的 `[实证]` 结论仅限本地可复现项**：token 倍率、漂移检出、跨 agent 落点、格式合规均已本地验证；**未验证**的是"这些机制在真实团队中是否降低了返工"——这需要 6.3 的基准来回答。
5. **调研方法**：定向搜索 + 官方文档核实，非系统综述。若需要更强证据，下一步应做的是 6.3 的基准实验，而不是扩大对比范围。
